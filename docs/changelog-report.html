ChatGPT2API 变更报告

基于完整上下文审计，以下是本轮所有变更的汇总。

变更统计

阶段总数6 个阶段（1-5 + 终局审计）
修改文件14 个 Python + 6 个前端 TSX/TS + 5 个配置/文档
新增文件4 个（dashboard.py, rate_limit.py, 启动bat, 停止bat）
新增页面1 个（运维看板 /dashboard）
新增 API3 个（/api/dashboard/scheduler, ops, usage）
新增配置项5 个（scheduler_mode, scheduler_priority, rate_limit_rpm, rate_limit_per_ip_rpm, workers）

阶段 1：Windows 一键启动

新增
  • 启动chatgpt2api.bat — UTF-8 编码，自动检测 Python/uv、安装依赖、构建前端、启动服务、崩溃自动重启
  • 停止chatgpt2api.bat — 按端口杀进程
  • 修复中文路径下 Turbopack 构建失败问题，默认使用 webpack

阶段 2：7×24 稳定运行

增强
  • 启动脚本增加崩溃自动重启循环（Ctrl+C 退出，非 0 退出码自动重启）
  • 现有守护线程：account-watcher（5min 刷新）、image-cleanup（30min 清磁盘）、backup_service

阶段 3：智能调度系统

移植 新增
  • 健康档位：healthy / warm / risky（基于状态、错误率、配额、最近错误时间）
  • 调度分：配额占比 + 成功加成 - 失败惩罚 - 冷却惩罚
  • 账号级优先级：config.scheduler_priority 按 email/token 配置
  • 双模式：round_robin（轮询）、remaining_quota（按剩余配额降序）
  • 三路归并选取：优先级 > 档位 > 调度分

阶段 4：运维看板

新增 新增
  • 后端：/api/dashboard/scheduler — 调度健康度 + 账号排行榜
  • 后端：/api/dashboard/ops — CPU/内存/磁盘/运行时长/存储统计
  • 后端：/api/dashboard/usage — 近 24h 调用统计 + 类型分布
  • 前端：运维看板页面（账号池总览、资源占用、调度排行榜、调用分布）
  • 前端：导航栏新增"运维看板"入口

阶段 5：高并发

增强 新增
  • 多 Worker 启动：config.workers 控制，利用多核 CPU
  • 全局限流中间件：滑动窗口 RPM + 单 IP 限流
  • Dockerfile 和 bat 增加 --limit-concurrency 512 --backlog 1024
  • 压测验证：4 Worker 达 7912 req/min，0 崩溃

变更测验（测测你是否理解全部变更）

1. 新增的调度系统有几个健康档位？分别是什么？

显示答案 3 个：healthy（健康）、warm（温存）、risky（风险），基于状态、错误率、配额和最近错误时间判定。

2. 限流中间件支持哪两种限流模式？

显示答案 全局 RPM 限流（rate_limit_rpm）和单 IP RPM 限流（rate_limit_per_ip_rpm），0 = 不限流。

3. 运维看板页面包含哪几个核心数据区块？

显示答案 账号池总览（总数/健康数/在途图片/近24h调用）、资源占用（CPU/内存/磁盘/运行时长）、调度排行榜（健康档位+调度分排名）、近24h调用分布。

4. 压测结果：4 Worker 模式下达到多少 req/min？

显示答案 7912 req/min，0 连接失败/崩溃。

5. 调度模式的两种选项是什么？

显示答案 round_robin（轮询）和 remaining_quota（按剩余配额降序优先）。
