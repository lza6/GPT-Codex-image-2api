2. 做了什么（改动明细）

2.1 版本对齐 + 前端指纹智能重建 根治版本停滞

根因（两个叠加）：① VERSION 文件一直是 2.8.0（落后于已发版的 2.8.1/2.8.2/2.8.3，存在版本漂移）；② 启动脚本旧逻辑只看 web_dist\index.html 是否存在，在就「前端已构建，跳过」——改了代码也不重建，UI 版本号（构建时从 VERSION 打包进静态文件）永远是旧值。

  • VERSION → 2.9.0，CHANGELOG.md 补 2.9.0 条目（含号池救活整节）。
  • 新增 scripts/web_stamp.ps1：对 web/src、web/public、web 根配置、VERSION、CHANGELOG.md 算 SHA256 指纹。
  • 启动chatgpt2api.bat 第 4/6 步改为：指纹与 web_dist/.build-stamp 不一致才 npm run build，一致则秒跳过。保证 UI 始终是新版本，又无变化不拖慢启动。
过程中抓到一个我引入的真 bug：首版补丁里 set /p "OLD_STAMP=<file" 把 < 写进了引号内，被当成提示字符串，导致 set /p 从控制台死等输入、启动脚本会挂起。靠实测（测试 bat 超时）抓到，已改为 for/f 读指纹文件并加 if not defined CUR_STAMP 守卫。这正说明「先测试再宣称完成」的必要性。

2.2 号池救活（71 个 passwordless 异常账号）本轮核心

根因（已实证）：这批号是 passwordless 注册、没有可用的 OpenAI 密码，密码登录返回 401；且同 IP 批量发码被 OpenAI 限流。必须走邮箱 OTP 救活。

3. 关键决策与直觉

  • Graph 优先、98faka 兜底，而非二选一硬切：方案已实测 Graph 可用且更优（国内直连、免第三方），但为稳妥保留 98faka 兜底；token 换不出才回退，读到箱无码不双轮询（同箱 98faka 也不会有，白等 90s）。
  • 指纹用「路径+大小+mtime」而非内容哈希：启动时快速判变是目标，内容哈希每次全量读太慢。git checkout 同内容会误触发一次重建——可接受的权衡（方向安全：宁可多建不漏建）。并排除了 next-env.d.ts/*.tsbuildinfo 这类每次 build 都会变、mtime 不代表源码改动的产物。
  • 遗留 71 号靠脚本+外部 payload，新号靠 watcher 自动救：遗留号导入时还没有 mail_credential 入库功能，池内无凭证，自动救活对它们结构性无效——这是诚实边界，不包装成「全自动」。
  • 变异 flaky 直接根治而非继续当边界：前七轮/十一轮都记为「已知 flaky 不追查」，本轮用子进程强制 UTF-8 一行改动根治——能根治的不该一直挂着。
  • 企业级特性（Kafka/分库/CDN/多副本）不硬塞：单机内部工具，性能优先、YAGNI。你要的限流/熔断/缓存/健康检查/可观测性/契约/施压/慢查询/SQL 项目早已具备（见第 6 节矩阵），不冒充新做。
