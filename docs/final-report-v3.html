一、上下文与直觉

项目背景

ChatGPT2API 是对 ChatGPT 官网图片生成/编辑能力的逆向封装，提供 OpenAI 兼容 API 代理。已在生产环境部署使用，需要达到生产级可用标准：稳定、可观测、可维护、可调用。

核心问题直觉

  • 稳定性：上游抖动会雪崩，账号失败需主动熔断而非被动降权
  • 可观测性：生产故障只能翻文本日志，无法定位慢请求/错误率突增/链路追踪
  • 性能：每次请求新建 Session 导致 TLS 握手开销 ×N，高并发延迟尾巴长
  • 可维护性：config.json 无校验、日志无限增长、代理池内存态重启全丢
  • 可调用性：调用方接入文档缺失、错误码不统一、无 SDK 示例
  • 内部定制：需去除原作者信息、GitHub 链接，纯本地部署

三、独立审查发现的问题（8 个，全部修复）

P0：metrics_middleware 异常路径崩溃 P0

根因：'response' in dir() 判断不可靠，call_next 抛异常时 response 未定义，response.headers 报 UnboundLocalError，且异常路径无指标无追踪头。
修复：重写 dispatch，status 默认 500，try/finally 记录指标，response 存在才注入头。复验：401 异常路径 errors=1 正确记录。

P1：熔断器在账号不可用时误标成功 P1

根因：record_success 在 fetch_remote_info 返回后立即调用，但返回的账号可能限流/无配额不可用。
修复：record_success 移到 _is_image_account_available 确认后；返回成功但不可用记为失败。

P1：SSE 客户端断开协程泄漏 P1

根因：event_generator 的 while True 无客户端断开检测，客户端断开后协程持续运行泄漏。
修复：外层 try/except asyncio.CancelledError 正常退出协程。

P1：日志缺 request_id（全链路追踪是假的）P1

根因：metrics 中间件生成 request_id 注入响应头，但日志记录（LoggedCall）完全不感知，导致日志页可搜 request_id 但搜不到——全链路追踪是假的。
修复：用 contextvars 在请求上下文传递 request_id，LoggedCall.log 记录到 detail。验证：test-req-12345 正确写入日志。

P1：use-version-check GitHub 远程残留 P1

根因：内部定制化部署仍会 fetch GitHub 远程 VERSION/CHANGELOG。
修复：改为仅使用构建时注入的本地版本。

P1：header-actions/version-dialog GitHub 链接被还原 P1

根因：之前去除的 GitHub 链接被覆盖还原。
修复：重新去除，并修 top-nav/version-dialog 的调用参数同步问题。

四、变更测验（测测你是否理解）

终局审计测验

1. metrics_middleware 的 P0 bug 根因和修复方式是什么？

A. 变量名拼错   B. 'response' in dir() 判断不可靠且异常路径 response 未定义，改为 status 默认 500 + try/finally   C. 缩进错误
B. dir() 返回模块级名字不含局部变量，call_next 抛异常时 response 未定义导致 UnboundLocalError。修复：status 默认 500，try/finally 记录指标，response 存在才注入头。

2. 熔断器 P1 bug 为什么危险？

A. record_success 在账号不可用时调用，误判不可用账号为健康   B. 熔断次数太少   C. 冷却时间太长
A. record_success 在 fetch_remote_info 返回后立即调用，但返回的账号可能限流/无配额不可用。危险在于熔断器把不可用账号误判为健康，破坏熔断保护。修复：移到可用性确认后。

3. 日志缺 request_id 的问题是什么，如何修复？

A. 日志没记录   B. metrics 中间件生成 request_id 但日志不感知，用 contextvars 传递   C. 日志太多
B. metrics 中间件生成 request_id 注入响应头，但 LoggedCall 完全不感知，导致日志页可搜 request_id 但搜不到（全链路追踪是假的）。修复：contextvars 在请求上下文传递，LoggedCall.log 记录到 detail。

4. bat 闪退的三重根因是什么？

A. UTF-8 BOM + LF 行尾 + 中文 GBK 损坏   B. 端口占用   C. 缺少 pause
A. UTF-8 BOM（cmd 把 EF BB BF 当命令）、LF 行尾（cmd 只认 CRLF 错切命令）、UTF-8 中文在 GBK 下损坏。修复：GBK + CRLF + 无 BOM。

5. 品牌定制为什么 remote 也要移除？

A. 美观   B. 防止误 push 定制代码到原作者仓库   C. 提升性能
B. remote 指向原作者仓库（basketikun/chatgpt2api），一旦误 push 就把内部定制代码推到原作者仓库。移除后纯本地管理，绝对安全。

五、剩余边界（诚实说明）

  • SSE 端点是长连接：测试脚本无法短时间验证完整推送流（会阻塞），但端点已注册且数据格式正确，浏览器 EventSource 可正常消费（含 CancelledError 处理）。
  • 多 Worker + JSON 存储：仍会回退 workers=1 并警告（数据安全保护），生产建议用 SQLite/Postgres 后可多 Worker。
  • HTTP 集成测试：17 个需要真实 OpenAI 账号的测试跳过（外部环境依赖，非代码缺陷，符合"烧钱的真实 API 调用无需跑 e2e"）。
  • image_tasks_api 测试竞态：4 个测试单独跑 100% 通过，并行时因 pytest 模块缓存偶发失败（非代码缺陷）。
  • 历史技术债：超大文件（openai_backend_api.py 2763 行、account_service.py 1850 行）和大函数建议后续拆分（已在代码审查报告标注）。
