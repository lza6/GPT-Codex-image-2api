一、本轮终局审计发现的 3 个真实缺口

P0：main.py 未初始化 PROMETHEUS_MULTIPROC_DIR P0

根因：prometheus-client 的 multiprocess 模式需要 PROMETHEUS_MULTIPROC_DIR 指向共享目录，各 worker 把指标写入，/metrics 从该目录聚合。main.py 没有初始化，多 Worker 下指标不聚合，只有单进程指标。
修复：main.py 启动时初始化共享目录（data/prometheus_multiproc），清空旧文件，设置环境变量。验证：多 Worker 时目录创建，单 Worker 时不设置。

P1：Session 池 invalidate 未被调用 P1

根因：session_pool.invalidate 存在但从未被调用。token 失效后 Session 不会被强制重建，导致用过期 Session（旧 cookie/会话）继续请求。
修复：remove_invalid_token 接入 session_pool.invalidate，token 失效时强制重建对应 Session。

P2：log_service.add 在 text 格式无 request_id P2

根因：只有 LoggedCall.log 会记录 request_id，但 log_service.add 直接调用的地方（account_service 5 处）在 LOG_FORMAT=text 时没有 request_id，全链路追踪不一致。
修复：log_service.add 统一注入 request_id（text 和 json 格式都带）。验证：test-add-direct-001 正确写入。

四、变更测验（测测你是否理解）

终局审计测验（第四轮）

1. prometheus multiprocess 模式为什么需要 PROMETHEUS_MULTIPROC_DIR？

A. 美观   B. 多 Worker 各写指标到共享目录，/metrics 从该目录聚合   C. 提升性能
B. prometheus-client 的 multiprocess 模式需要各 worker 把指标写入共享目录，/metrics 端点从该目录聚合所有 worker 的指标。main.py 启动时初始化该目录。

2. Session 池 invalidate 为什么必须在 remove_invalid_token 时调用？

A. 美观   B. token 失效后用过期 Session（旧 cookie）继续请求会失败   C. 提升性能
B. token 失效后 Session 不会被强制重建，导致用过期 Session（旧 cookie/会话）继续请求。remove_invalid_token 接入 invalidate 强制重建。

3. log_service.add 为什么要在 text 和 json 格式都注入 request_id？

A. 美观   B. 只有 LoggedCall 有 request_id，直接 add 调用漏了，全链路追踪不一致   C. 提升性能
B. 只有 LoggedCall.log 记录 request_id，log_service.add 直接调用在 text 格式没有，导致全链路追踪不一致。统一注入保证一致性。

4. metrics_middleware 的 P0 bug 根因是什么？

A. 变量名拼错   B. 'response' in dir() 判断不可靠且异常路径 response 未定义   C. 缩进错误
B. dir() 返回模块级名字不含局部变量，call_next 抛异常时 response 未定义导致 UnboundLocalError。修复：status 默认 500，try/finally 记录，response 存在才注入头。

5. 熔断器 record_success 为什么必须在可用性确认后调用？

A. 美观   B. fetch_remote_info 返回的账号可能限流/无配额不可用，误判为健康   C. 提升性能
B. record_success 在 fetch_remote_info 返回后立即调用，但返回的账号可能限流/无配额不可用。危险在于熔断器把不可用账号误判为健康，破坏熔断保护。修复：移到可用性确认后。

五、剩余边界（诚实说明）

  • SSE 端点是长连接：测试脚本无法短时间验证完整推送流（会阻塞），但端点已注册且数据格式正确，浏览器 EventSource 可正常消费（含 CancelledError 处理）。
