三、独立红队审查（对平庸懒惰零容忍）与修复闭环

用户要求"独立审查线程，只验证不改代码，修复清单交回主线程修复，持续循环直到通过"。本轮严格走此流程：审查 → 修复 → 复验（Approve）。

Blocking 1：CI 测试门必挂（环境污染）Blocking

根因：test_account_image_capabilities.py:9 模块级 os.environ.setdefault("CHATGPT2API_AUTH_KEY","test-auth") 在导入时污染全局环境，ConfigStore.auth_key 每次读 os.getenv，导致按字母序排在其后的测试 Bearer chatgpt2api 全部 401。基线 2 失败被本轮扩到 9。
修复：新建 test/conftest.py autouse fixture 用 monkeypatch 固定 auth-key。结果 9 failed → 0 failed（161 passed）。复验确认闭环。

Blocking 2：熔断误判——业务拒绝当上游抖动Blocking

根因：record_failure 用反向白名单 not is_token_invalid_error，任何非 token 失效的异常都记熔断失败——包括内容审核 400、prompt 违规。后果：5 个用户连续发违规内容就把健康账号熔断 30s，恶意用户可逐个熔断整个账号池造成拒绝服务。熔断语义应是"上游抖动"，业务 4xx 是上游正常工作的证据。
修复：新增 is_upstream_instability_error 正向白名单（5xx/超时/TLS/连接），仅命中才 record_failure。复验确认 moderation 400 不再触发熔断。

四、契约核验发现的隐藏真 bug（最有价值）

看板用量统计恒为空（字段错位）P1

根因：_collect_log_stats 读 created_at 与顶层 status，但日志实际写的是 time(text)/ts(json) + detail.status。实测：注入 5 条当天日志，/api/dashboard/usage 仍返回 {total_24h:0, failed_24h:0}——看板"近24h调用"卡片从上线起就恒空，契约形同虚设。
修复：兼容 time/ts/created_at + detail.status 兜底。实测修复后：total_24h>0、failed_24h>0、by_summary/recent 有真实数据。

chunked 传输绕过请求体限制P1

根因：仅查 Content-Length 头，无 Content-Length 的 chunked 传输直接放行。实测：11MB chunked body 返回 422（进路由解析）而非 413——10/50MB 上限形同虚设。
修复：API 写请求无 Content-Length 且 chunked 时返回 411 Length Required（OpenAI SDK/curl 客户端总带 Content-Length，不影响正常调用）。

八、变更测验（测测你是否理解）

终局审计测验（第五轮）

1. 熔断器 record_failure 为什么必须用 is_upstream_instability_error 正向白名单，而非 not is_token_invalid_error 反向白名单？

A. 性能更好   B. 业务拒绝(内容审核400/prompt违规)是上游正常工作证据，误记会让恶意用户熔断健康账号造成拒绝服务   C. 代码更短
B. 反向白名单把任何非 token 失效异常都记失败，包括业务 4xx。5 个用户连续发违规内容就熔断一个健康账号 30s，恶意用户可逐个熔断整个账号池。正向白名单只在 5xx/超时/TLS/连接等真上游抖动时记失败。

2. test_account_image_capabilities.py 为什么会导致 CI 9 个测试 401 失败？

A. 测试写错了   B. 模块级 os.environ.setdefault 在导入时污染全局 auth-key，ConfigStore 每次读 os.getenv 导致后续测试的 Bearer chatgpt2api 失效   C. 网络问题
B. 模块导入时 setdefault("CHATGPT2API_AUTH_KEY","test-auth") 改写全局环境变量，ConfigStore.auth_key 是 property 每次读 os.getenv，按字母序排在其后的测试全部 401。修复：conftest.py autouse fixture 固定并复原 auth-key。

3. 看板"近24h调用"卡片为什么从上线起就恒为空？

A. 没有日志   B. _collect_log_stats 读 created_at/顶层 status，但日志实际写 time/ts + detail.status，字段错位导致统计恒 0   C. 前端没渲染
B. 日志 text 格式写 'time'、json 格式写 'ts'，成败状态在 detail.status 子对象，但统计代码读 'created_at' 和顶层 'status'——全部对不上，实测注入日志仍返回 0。修复后实测有真实数据。

4. 请求体限制为什么对 chunked 传输形同虚设？怎么修？

A. 不用修   B. 仅查 Content-Length 头，无 Length 的 chunked 直接放行；修为 API 写请求无 Content-Length 且 chunked 时返回 411   C. 改成 100MB
B. 实测 11MB chunked 返回 422（进路由）而非 413。OpenAI SDK/curl 客户端总带 Content-Length，故对无 Length 的 chunked API 写请求返回 411 Length Required，堵住绕过且不影响正常客户端。

5. 为什么本轮没有直接把 OpenAIBackendAPI 的 Session 换成 session_pool.get()？

A. 忘了   B. 每个 backend 有独立指纹(fp/device_id)注入 session.headers，同代理多账号共享 Session 会互相覆盖 Authorization/device_id 导致串号——池化 key 需含账号标识，登记 v2.1 专项设计   C. 性能问题
B. Session 池按(代理,impersonate,verify)缓存，但 __init__ 会把独立指纹和 Authorization 写进 session.headers，同代理下不同账号共享同一 Session 会互相覆盖——串号是 P0 正确性风险。正确池化 key 必须含账号标识。

6. 本轮审计方法论上最关键的一步是什么？

A. 多写测试   B. 发现权威需求源(计划书/下一步改进指南.md)并以 S1-S8 为准，避免自创框架自说自话闭环；再用多代理核验+独立红队审查交叉验证，揪出"宣称闭环实际未接线"的伪闭环   C. 改更多代码
B. 前四轮 N1-N21 是在不知道指南的情况下自创的。本轮对齐权威需求源，并用红队审查"有罪推定"揪出熔断未接线、用量统计恒空、chunked 绕过等真实伪闭环，再修复并复验（Approve）。
