# 产品策略分析（第七轮 · 资深产品总监视角）

> 生成日期：2026-08-02
> **定位前提**：本项目是**内部自托管工具**（画图为主的生产力工具，逆向研究性质），
> 不是多租户 SaaS。以下分析按"内部工具的稳健演进"为主线，SaaS 化视角仅作参考，
> 涉及商业化合规风险的部分明确标注**不建议**。

---

## 1. 产品定位还原

| 维度 | 现状 | 证据 |
|------|------|------|
| 核心价值 | 把 ChatGPT 官网的图片/对话能力封装成 OpenAI 兼容 API，供内部系统调用 | README + api/ai.py |
| 用户 | 项目方自己 + 可能的少量协作者（外包文档存在） | docs/onboarding/README-contractor.md |
| 关键约束 | 逆向研究、不商用、号池是稀缺资源（封号成本） | README 免责声明、熔断/限流的设计动机 |
| 真实瓶颈 | 账号健康（封禁/限流）> 代码性能 | 调度/熔断/代理池三大子系统都围绕"账号存活" |

**结论**：这个产品的"用户体验"本质是**账号池的可用率与透明度**——调用方只关心
"发请求能不能稳定出图"，运维者只关心"哪个号要死了、为什么"。

## 2. 用户体验差距分析（按真实使用旅程）

### 调用方旅程：发请求 → 拿图
| 环节 | 现状 | 差距 | 建议优先级 |
|------|------|------|-----------|
| 接入 | OpenAI 兼容 + 契约文档 + SDK 示例 | 已闭环（N13） | — |
| 失败理解 | 错误经 public_image_error_message 转译 | 调用方拿不到"哪个账号、什么真实原因"（合理，防泄漏） | P3 现状正确 |
| 重试 | retry_budget 已内建幂等/流式分级 | 调用方无需关心 | — |

### 运维者旅程：看板 → 判断 → 处置
| 环节 | 现状 | 差距 | 建议优先级 |
|------|------|------|-----------|
| 发现问题 | 看板 + 熔断列 + SSE 实时推送 | **无主动告警**：号批量死掉要人盯看板才发现 | **P2 最高价值项**：webhook 告警（账号池健康度 < 阈值时推送） |
| 定位原因 | 日志按 request_id 全链路可查；**账号维度数据已落盘**（`detail.account_email`，`log_service.py:389`） | **缺按账号过滤的查询通道**：`/api/logs` 仅支持 type/start_date/end_date（`api/system.py:130-133`），无法按 account_email 聚合 | P2（数据已有，只差过滤参数） |
| 处置 | 驱逐失效 token、刷新、重登录都有 | 处置动作分散在不同页面 | P3 |
| 预防 | 健康档位 + 调度分自动规避（`_account_health_tier`/`_account_dispatch_score`，`account_service.py:161-209`） | 缺"账号寿命预测" | P3（**数据完全可复用**，见下方论证） |

### 最大体验缺口（诚实判断）
**主动告警是唯一真正的闭环缺口**。其余环节（发现→定位→处置）工具链已完整，
但起点仍依赖"人主动来看"。一个最小实现：后台任务周期算一次健康账号占比，
低于阈值时 POST 到配置的 webhook URL（企业微信/钉钉/自定义）。**实现成本修正**：
- 数据侧无需新建——`_collect_account_health`（`api/dashboard.py:26-48`）已算出 healthy/warm/risky/banned 分布，SSE 每 3s 已在推送
- 但"100 行闭环"是**后端骨架**口径；按项目"六步配置"惯例（config.json + config.py getter + .env.example + 前端 config-card.tsx + settings store + api.ts）+ 后台任务 + 测试 + 契约探测，**真实落地约 200-300 行**，不是 100 行
- 若接受纯后端极简版（无设置页 UI、仅 config.json 字段），可压到 ~120 行，但运维者需手改配置文件，不符合"一次调用就能跑通"的门槛目标

### 补充视角 A：账号寿命预测的数据可行性（原文漏评）
原文把"账号寿命预测"标 P3 且说"调度分已部分覆盖"，但**未指出预测所需的全部输入已经存在**：
- 每账号累计 `success`/`fail` 计数（`account_service.py:317-318` 落盘，调度分公式直接消费，`account_service.py:197-203`）
- 最近错误时间戳 `last_refresh_error_at`/`last_token_refresh_error_at`（`account_service.py:205-208`，已参与冷却惩罚）
- 日志逐条含 `detail.account_email`（`log_service.py:389`），可回溯单账号成败时间线

因此"寿命预测"不是要不要做的问题，而是**把已消费的同一批信号改写成趋势形态**
（近 N 次失败率斜率）即可，无需新增埋点。建议并入 P2 聚合页，而非单列 P3。

### 补充视角 B：看板 UX 的真实缺口（原文想象的缺口 vs 代码实证）
通读 `web/src/app/dashboard/page.tsx` 后，真实缺口不是"数据不够"，而是**呈现粒度**：
- 调度排行榜只 `slice(0, 10)`（page.tsx:183），**风险档账号若排在 10 名外永不可见**——
  这正是"哪个号要死了"最该被看见的集合，却在 UI 上被截断
- 风险/温存档与 healthy 档混排在同一表格，无独立筛选/置顶
- "定位原因"环节说的"缺账号维度聚合视图"，**本质是后端过滤参数缺失**（见上表），
  前端无需大改，加一个 `account_email` 过滤即可支撑单账号时间线

## 3. 增长/商业化视角（明确边界）

| 方向 | 判断 | 理由 |
|------|------|------|
| 多租户 SaaS 化 | **不建议** | 逆向研究定位，商用违反上游 ToS，且账号池模式无法规模化的根本原因在上游风控而非代码 |
| 卖给第三方部署 | **不建议** | 同上，法律风险不可控 |
| 内部提效深化 | 建议 | 告警、账号寿命预测、批量导入模板是安全的演进方向 |
| AI 赋能付费场景 | 不适用 | 本产品即 AI 能力的搬运层，无自有增值空间可收费 |

## 4. 工程侧建议（与产品价值挂钩）

1. **P2 主动告警 webhook**（上面已述，含成本修正）——投入产出比最高的下一功能
2. **P2 账号维度聚合页**——不是"散在日志里"：`detail.account_email` 已落盘，
   只需给 `/api/logs` 加 account_email 过滤参数 + 前端按账号渲染时间线，后端改动 < 30 行
3. **P2 排行榜风险账号可见性**——调度排行榜 slice(0,10) 截断了最该被看见的风险档，
   加"仅看 risky/warm"筛选即可（纯前端，`web/src/app/dashboard/page.tsx:183`）
4. **P3 容量规划报表**——按 logs.jsonl 历史算"日均出图量 vs 账号数"，
   回答"要加几个号才能扛住 X 张/天"（注意：慢查询报告已登记 logs.jsonl 全量读为热点，
   该报表应读切分后的日志或聚合缓存，而非再全量扫一遍）
5. **不做**：多租户、计费、权限体系细化（内部工具无此需求，YAGNI）

## 5. 本分析的诚实边界

- 未做真实用户访谈（用户即项目方本人），结论基于代码与文档证据推演
- "告警是最大缺口"的判断依据：其余旅程环节在 workflow_status.md 均有闭环证据；
  告警链路已全量 grep（services/ + api/ + main.py 搜 webhook/alert/notify），
  仅命中并发原语 `notify_all()` 与弱口令告警 docstring，无任何告警通道实现
- "实现成本 200-300 行"是**估算**，依据是项目既有配置项的改动面（见 config-card.tsx
  六步链路），非实测工时
- SaaS 化"不建议"的判断基于 README 免责声明与逆向定位，非技术不可行

| 5 | （漏评）看板 UX 缺口 | 真实缺口是**呈现粒度**：调度排行榜 slice(0,10) 截断风险档账号，"要死的号"在 UI 上不可见 | `web/src/app/dashboard/page.tsx:183` |

**审视结论**：原文主线判断（告警是最大缺口、SaaS 化不建议）经抽查**成立**，予以保留。
修正集中在三处——把"缺数据"还原为"缺查询通道"、把"100 行"修正为"200-300 行（含六步链路）"、
补充寿命预测的数据可行性证据与看板排行榜截断的真实 UX 缺口。

**本文件仍站不住的地方（诚实登记）**：
- "200-300 行"仍是估算，未经实际编码验证，偏差可能 ±50%
- "告警是最高价值项"的排序依赖"号批量死是高频痛点"这一假设，该假设无运行数据支撑
  （项目方未提供历史封号频率），若实际封号极少发生，告警价值排序应下调
- 视角 B 的"风险档永不可见"在账号数 ≤10 时不成立，该缺口随号池规模放大才显现
