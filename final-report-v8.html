2. 直觉与关键判断

直觉 1：PRAGMA 不是设一次就完事。 SQLite 的 busy_timeout 和 synchronous 是每连接级设置——连接池里每条新连接都要重放。第一版只在初始化连接上设置，测试还通过了（连接池复用了同一条连接，假阳性）。反向批判揪出后改为 SQLAlchemy connect 事件监听器，对池内每条连接生效。journal_mode=WAL 则不同，它持久化在 DB 文件头，设一次即可。

直觉 2：TTL 判定不能用 wall clock。 进度记录的过期判断若用 time.time()，系统时间跳变/NTP 校时会让记录"永不过期"或"立刻过期"。改用 time.monotonic()——单调时钟只走不倒。

直觉 3：monotonic 时间戳绝不能出 API。 进程内单调秒数对任何外部消费者都无意义，还会被契约快照记录为"未经申报的契约变更"。出口处统一过滤。

直觉 4：类属性共享字典 + 实例级 TTL = 跨实例误删。 这是独立审查抓到的最狠一条：进度字典原本是 class 级共享，一旦不同实例持有不同 TTL，短 TTL 实例会把长 TTL 实例的活记录清掉。修复不是"加注释说明"，而是直接挪为实例属性根治。

5. 边界与剩余风险

  • WAL 模式在 :memory: 数据库上无效（SQLite 本身限制），本项目工厂只用文件路径，不受影响。
  • 关闭 WAL 不联动关闭 synchronous=NORMAL——已在 docstring 声明，属有意设计。
  • 配置层 TTL 最小 1s，亚秒级仅供测试经构造参数传入——语义分层已文档化。
  • 真实多 worker（多进程）并发写只在单进程线程池压测下验证；跨进程场景 WAL 是 SQLite 官方标准解法，行为由 SQLite 保证。
  • 其余 17 项登记缺口（D1–D4、D6–D7、D9–D19）不在本轮范围，仍在 v2.1 清单中。

6. 变更测验（必须全部答对）

Q1：为什么 busy_timeout 和 synchronous 必须通过 SQLAlchemy connect 事件监听器设置，而不是初始化时执行一次？
答案：b。busy_timeout/synchronous 作用于单个连接，连接池后续新建的连接是全新连接，必须经 connect 事件逐条设置。journal_mode=WAL 不同——它持久化在 DB 文件头，设一次即可。
Q2：进度记录 TTL 判定为什么用 time.monotonic() 而不是 time.time()？
答案：c。wall clock 可能被校时回拨或跳变，导致记录"永不过期"（内存泄漏复活）或"立刻过期"（进度查询 404）。monotonic 只走不倒，是 TTL/超时场景的正确时钟。
Q3：独立审查的 Critical 1 是什么，如何根治？
答案：b。class 级 dict 被所有 AccountService 实例共享，而 TTL 是实例属性——短 TTL 实例 prune 时会清掉长 TTL 实例未过期的记录。修复不是加注释，而是把字典和锁挪入 __init__ 成为实例属性，并补跨实例隔离防回归测试。d 是 Suggestion 级，a 不存在，c 是误报（int 强转后无注入面）。
Q4：created_at（monotonic 秒数）为什么必须在 API 出口过滤？
答案：a。monotonic 是进程启动以来的秒数，任何 API 消费者都无法解释；且 contract_probe 快照 diff 会把它当成契约变更。项目里同名 created_at 字段在日志体系是 wall time，同名两种时钟语义并存是埋雷。出口经 _public_progress 统一 pop。
Q5：本轮"配置接入 6 步"指的是哪 6 步？
答案：d。这是项目工作流技能规定的配置项接入完整链路，缺一不可——漏掉任何一步都会出现"配置存在但不生效"或"前端看不到"的断链。本轮 sqlite_wal_mode / sqlite_busy_timeout_ms / progress_ttl_seconds 三项均按此链路接入。
