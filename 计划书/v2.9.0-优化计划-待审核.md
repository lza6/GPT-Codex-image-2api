### P0 - 账号体系（用户第 1、4、10 问 + 中途插入的"异常账号自动获取 ey token"）

#### 1.1 异常账号根因可视化（用户第 4 问核心痛点）

**现状**（调研代理深挖）：后端**已存 5 个错误字段**（全在 `_normalize_account` 保留，`account_service.py:381-385`）：
- `last_refresh_error` + `last_refresh_error_at`（最近刷新错误，`:1690-1691` 写入）
- `last_token_refresh_error` + `last_token_refresh_error_at`（token 刷新错误）
- `invalid_count` + `last_invalid_at`（累计失效次数 + 最近失效时间，`:1688-1689`）
- `login_error`（密码导入失败类型，仅 pending 占位账号，`:1493`）

但前端 `Account` 类型（`web/src/lib/api.ts:19-53`）**5 个字段全未声明**，表格列（`page.tsx:1376-1389`）无"错误原因"列 → 用户看不到原因。`data/accounts.json` 里可直接看到这些字段。

**触发"异常"的 5 条路径**（`remove_invalid_token` → `:1281/:1295` 标 status=异常 + quota=0）：
| 路径 | 触发条件 | 证据 |
|------|---------|------|
| A. 上游 InvalidAccessTokenError | `/backend-api/me` 返回 401，刷新后仍 401 | `account_service.py:1760-1786` |
| B. refresh_token 过期 | OAuth refresh 失败，invalid_count≥2 且距上次失效>confirm_seconds | `account_service.py:1673-1703` |
| C. 密码重登失败 | `_password_re_login_thread` 返回 ok=False（非 account_deactivated） | `account_service.py:696-716` |
| D. 密码登录异常 | `_login_with_password` 抛 Exception | `account_service.py:717-732` |
| E. 需要验证码 | 登录返回需要 OTP/captcha | `account_service.py:892` |

**关键澄清**：`auto_remove_invalid_accounts=True` 时直接物理删除异常账号；`=False` 时只标"异常"+quota=0（不删）。用户 75 个异常说明该配置当前 =False。

**方案**：
1. 前端 `Account` 类型补声明 5 个错误字段（`web/src/lib/api.ts:19-53`）
2. 账号列表新增列"异常原因"（`web/src/app/accounts/page.tsx:1376-1389`）：
   - 当 `status === "异常"` 时展示 `last_refresh_error`（截断 80 字符）+ `last_refresh_error_at` 相对时间
   - tooltip 展示完整错误 + `invalid_count`
   - 非异常账号该列显示 "—"
3. 后端 `list_accounts` / `get_stats` 确认这些字段已透传（`_normalize_account` 已保留，需验证 API 序列化不丢字段）

**验收**：
- 异常账号列表每行能看到具体错误（如 "oauth_refresh_http_401: invalid_grant" / "invalid_access_token" / "password_relogin_failed"）
- tooltip 显示完整错误 + 时间戳 + invalid_count

#### 1.2 异常账号自动获取新 access_token（用户中途插入消息核心诉求）

**现状**：已有双重续 token 机制，但只在 `refresh_accounts`（手动一键刷新）时触发。用户要的是"异常账号自动恢复"。

**方案**：
1. 扩展 `account-watcher`（`api/support.py:126-159`）增加第二职责：
   - 现有：5 分钟一轮，检查 limited + normal + expiring access tokens + refresh_token keepalive（3 天保活，批次 3，失败退避 6 小时）
   - 新增：扫描所有 `status=异常` 且 `invalid_count >= 2` 的账号，自动调 `fetch_remote_info` 尝试恢复（preflight refresh + force refresh + 重登）
   - 间隔：默认 30 分钟（可配置 `abnormal_auto_recover_interval_minutes`）
   - 并发：max 5 workers，避免雪崩
2. 恢复成功 → 状态转"正常"，清 `last_refresh_error`，记审计日志
3. 恢复失败 → 保持异常，`invalid_count` 不再涨（避免反复刷），记日志
4. 前端"尝试恢复异常账号"按钮复用同一逻辑（手动触发）
5. **关键限制提示**（调研代理发现）：现有"恢复"按钮走 `re_login_accounts`（`account_service.py:2013-2071`），对**无 email/password 的纯 token 账号直接 skip**（`:2043-2047`）。75 个异常账号若是纯 token 导入（source_type=web），恢复按钮无效。方案：扩展恢复逻辑，对纯 token 账号先调 `fetch_remote_info`（refresh_token 换 token 路径，路径 A/B 恢复），只有 refresh_token 也过期才走密码重登
6. 恢复按钮选中的异常账号若无 password，前端提示"这些账号无邮箱密码，仅尝试 refresh_token 恢复"

**验收**：
- 异常账号 30 分钟内自动尝试恢复（无需手动点按钮）
- 恢复成功的账号状态变"正常"，quota 恢复
- 审计日志记录每次自动恢复尝试
- E2E：构造一个 `status=异常` 的账号，watcher 跑一轮后调用了 `fetch_remote_info`

#### 1.3 一键刷新与额度真实性（用户第 1、9 问）

**现状**（调研代理深挖）：
- 一键刷新：前端 `handleRefreshAccounts`（`page.tsx:485-513`）→ `refreshAccounts` API（`api.ts:453`）→ `POST /api/accounts/refresh`（`api/accounts.py:353-372`）异步返回 `progress_id`，后台 `refresh_accounts`（`account_service.py:1925-2011`）max 10 并发，每个账号调 `fetch_remote_info` → 上游并发 3 线程调 `/backend-api/me` + `/conversation/init` + `/accounts/check` → 取 `limits_progress[image_gen].remaining` 作为真实 quota（`openai_backend_api.py:380-389`）
- watcher 周期 **默认 5 分钟**（`config.py:353`），每轮 `refresh_accounts` 用上游真实 quota **覆盖**本地累计值（`account_service.py:146` → `fetch_remote_info` → `update_account`）
- 额度扣减 `mark_image_result` 每次 success 扣 1，无双扣 bug（`account_service.py:1717-1720`，唯一成功扣减点 `conversation.py:1568`）

**"540→538" 现象根因**：不是双扣，而是 **watcher 5 分钟一轮用上游真实 quota 覆盖本地**。用户调用前看到的 540 是某次刷新后的快照，调用后看到 538 可能是 watcher 在期间又刷新了一次（上游 quota 比本地少 2，或期间其他请求也消耗了）。这是**正常校正行为**，不是 bug。

**方案**（仅微调，不改核心逻辑）：
1. 前端"一键刷新"按钮加 loading 态 + 进度条（已有 `init_refresh_progress` + `fetchRefreshProgress` 300ms 轮询，确认前端接上）
2. 额度扣减增加单测断言"一次文生图成功只扣 1"（已有 `test_mark_image_result_consumes_quota`，补一个"续轮询成功也只扣 1"的测试）
3. 调用日志详情里展示该请求实际消耗的账号 + 是否切换过账号（续轮询切换账号会扣不同账号的 quota，总 quota 看起来扣 2 是正常的）
4. 前端剩余额度卡片加"上次刷新时间"tooltip，让用户理解 quota 会被上游覆盖

**验收**：
- 一键刷新有进度反馈
- 单测覆盖"续轮询成功只扣 1"
- 调用日志详情能看到本次请求用了哪些账号（可能多个）
- 剩余额度卡片显示上次刷新时间

### P1 - IP 池增强（用户第 11、12、13 问）

> **CRITICAL 前置发现**：IP 池存在**设计断层**——`proxy_pool.select()` 在业务代码零调用，实际请求走 `account.proxy` 字段（完整 URL 字符串），由 `proxy_settings.build_session_kwargs()` 解析，池里加的代理不会被任何请求使用。本批次必须先修复这个断层，否则后续增强都是空中楼阁。

#### 2.0 修复 IP 池设计断层（前置必做）

**现状**：`session_pool.py:77` 走 `build_session_kwargs(account=account)`，account.proxy 为空时回退 global/runtime，**从不调用 proxy_pool.select()**。

**方案**：在 `proxy_service.get_profile()`（`proxy_service.py:170-217`）的代理优先级链中插入"池选择"层：
```
新优先级：account.proxy（若绑定池条目）> proxy_pool.select()（若账号未绑定且池启用）> runtime > explicit > global
```
1. 账号 `proxy` 字段语义升级：若值等于池里某条目的 `url`，则视为"绑定该池条目"；若是独立 URL 则保持现状（向后兼容）
2. 账号未设 proxy 且池非空 → `proxy_pool.select()` 取一个健康代理
3. 健康检查结果（isolated）真正影响路由：select() 已排除非 HEALTHY 代理

**验收**：
- 池里有 3 个代理，账号未绑定 → 3 次请求 round_robin 轮询用这 3 个
- 池里某代理 isolated → 该代理不被选中
- 已绑定 account.proxy 的账号不受池影响（向后兼容）

持久化 `proxies.json` 升级，旧数据自动迁移（从 url 反解析）。

### P2 - 文生图稳定性（用户第 2、3、7 问）

#### 3.1 文生图失败根因排查与改进

**现状**（调研代理深挖）：duration=0.00s 失败 = **调度阶段瞬间失败**（handler 在 threadpool 里直接抛异常，未触达上游 HTTP）。三条具体路径：
1. **号池无可用账号**：`_list_ready_candidate_tokens` 返回空 → `account_service.py:1118` 抛 `RuntimeError("no available image quota")`。拒选条件 `_is_image_account_available`（`:159-163`）：`quota==0` 或 status∈{禁用,异常}（`:1281/:1295` 把异常账号 quota 置 0）
2. **熔断器 OPEN**：`circuit_breaker_registry.get(token).allow_request()` False（`conversation.py:1495-1502`）→ 抛 `ImageGenerationError("account circuit open")`。阈值：连续 5 次失败 OPEN，30s 冷却（`circuit_breaker.py:171-175`）
3. **fetch_remote_info 远程校验失败**：`:1187-1191` token 远程校验失败 → record_failure + continue 换号，20 次都失败 → `:1216` 抛 RuntimeError

"续轮询"不是主链路，是 `image_task_service._run_resume_poll`（`:491-631`）针对已超时失败任务的续等机制。

**方案**：
1. 失败日志详情补充"失败阶段"字段：`no_available_account` / `circuit_open` / `quota_zero` / `cf_blocked` / `upstream_error` / `network_timeout`，在抛异常处打标
2. `stream_image_outputs_with_pool` 失败时记录每个账号的具体失败原因到调用日志
3. 续轮询失败自动切换账号重试（已有逻辑，确认 max retries 合理，默认 `MAX_POLL_TIMEOUT_RETRIES=4`）
4. 前端调用日志列表"简述"列显示失败阶段，而非统一的"文生图调用失败（续轮询）"

**验收**：
- 失败日志详情能看到具体阶段 + 具体账号 + 具体错误
- 同一请求多次失败切换了哪些账号都记录

### P4 - CF 人机验证现状说明（用户第 8 问）

**现状（不改，仅说明）**：三层机制已健全：
1. **cf_solver**（`services/otp_login_service.py:81-270`）：本地 Camoufox 服务，OTP 登录时过 CF WAF，返回 cf_clearance + 全 cookie
2. **flaresolverr**（`services/proxy_service.py:105-148`）：外部 flaresolverr 服务，代理 clearance 模式用
3. **curl-cffi impersonate**（`services/session_pool.py:50-84`）：`impersonate="chrome110"` 指纹伪装，所有上游请求默认启用

**用户需知**：CF 拦截导致的文生图失败，根因是账号 cf_clearance 过期或代理 IP 被 CF 标记。改进方向：
- 文生图失败时检测 CF 拦截特征（响应含 `cf-mitigated` 头 / 403 + `cloudflare` / `Just a moment` 页面）→ 自动触发 cf_solver 或 flaresolverr 刷新 clearance → 重试 1 次
- `is_cf_blocked_error` 判定函数新增（参考 `is_token_invalid_error` 模式，`conversation.py:86-93`）
- 重试时强制重建 session（清旧 cookie + 重新过 CF）

**验收**：
- 构造 CF 拦截响应 → 触发自动刷新 clearance → 重试成功
- 非 CF 错误不触发该路径（避免误重试）
