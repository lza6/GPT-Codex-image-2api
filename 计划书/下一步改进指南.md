# ChatGPT2API 下一步改进指南（v2.8.0 → v5.x）

> **定位**：本文件是本项目「计划书」文件夹的核心迭代蓝本，供任何 AI 或开发者据此刻画版本。
> 每一章都是「现状（真实代码依据）→ 问题 → 方案 → 落地步骤 → 验收标准 → TDD 清单」的完整闭环，
> **禁止假实现**：每一条落地后必须跑通测试、防线、E2E，并在 `workflow_status.md` 登记证据。
>
> - 基线版本：**v2.8.0**（2026-08-05，399 测试全绿 / 五道防线全 PASS / 契约断链=0 / E2E 9/9）
> - 目标版本：v3.3（安全纵深）→ v3.4（可观测性）→ v4.0（架构演进）→ v5.x（高级特性）
> - 总原则：**不重构没坏的东西，不重复造轮子**，优先改造既有实现；每个改进独立可回滚。

## 0. 使用说明

### 0.1 这份指南怎么用

1. 按「优先级 + 依赖」选取下一个版本批次（见第 2 章路线图）。
2. 从对应章节复制「落地步骤 + 验收标准 + TDD 清单」到你的任务列表。
3. 每完成一项，必须：`uv run pytest` 全绿 → `scripts/run_all_guards.py` 全 PASS → 前端 `tsc + build` → 契约 `contract_guard --update`（若改字段）→ 更新 `workflow_status.md` 与 `CHANGELOG.md`。
4. 改 API 字段必须跑 `scripts/contract_probe.py` 与 `test/test_contracts.py` 双验证。
5. 前端改动必须跑 `scripts/e2e_smoke.cjs` 真实浏览器冒烟，并**同步 web_dist**（bat 仅在 web_dist 缺失时构建）。

### 1.4 真实瓶颈分析（第一性原理）

1. **账号存活是产品核心价值**：号池可用率 > 一切。调度/熔断/寿命预测/告警/探活/审计已围绕它建闭环，但「自动化处置」（自动降级、自动重登、自动隔离）仍多为半自动。
2. **安全纵深已补审计，但密钥轮换仍缺**：v2.8.0 补齐管理操作留痕 + 登录留痕；但单一 auth-key 无轮换路径、无角色细分仍存在。
3. **可观测性偏指标、缺日志检索**：Prometheus 指标齐全，但日志为文本行，无结构化字段过滤、无 Trace 关联、无日志聚合看板。
4. **架构演进空间**：3 大后端文件仍超 1800 行；协议接入仍是改主类；多实例部署无指南。
5. **前端体验已到 8 成**：异步按钮/骨架/分页/审计 tab 已落地，但 accounts/image-manager 大表无虚拟滚动、无深色主题、无国际化骨架。

## 3. P0 · 安全纵深（v3.3）

> 目标：把「单一 auth-key + 已留痕」升级为「可轮换 + 可细分角色」，补齐 v2.x/v3.2 安全边界的剩余短板。

### 3.1 密钥轮换机制

**现状分析（真实代码依据）**：
- 认证仅一个 `auth-key`，用环境变量 `CHATGPT2API_AUTH_KEY` 覆盖（services/config.py `_normalize_auth_key`）。
- 无轮换路径：改 key 必须手动改配置并重启，旧 key 立即失效，无宽限期。
- `config.py` 启动时 `_warn_if_weak_auth_key` 已做弱口令检测（production 拒绝启动），但没有「定期轮换提醒」。

**问题**：
1. key 泄露后只能人工改配置 + 重启，无审计追踪。
2. 无「新旧双 key 宽限期」，轮换时调用方全部瞬间 401。

**方案**：
1. 新增 `services/auth_service.py` 增强：支持多 key 列表（`auth_keys: list[str]`，兼容旧单字符串）。
2. 新增 `POST /api/system/rotate-auth-key`（require_admin，审计自动留痕）：生成新 key → 写配置 → 旧 key 进宽限期（`auth_key_grace_seconds`，默认 3600）→ 过期移除。
3. 前端设置页「安全」区：显示 key 列表 + 轮换按钮 + 宽限期倒计时。
4. 轮换事件自动写入审计日志（v2.8.0 已具备 require_admin 埋点，rotate 端点天然留痕）。

**落地步骤**：
- [ ] `config.py` 支持 `auth_keys` 列表（兼容 `auth-key` 单值，归一化为列表）。
- [ ] `api/system.py` 新增 rotate-auth-key 端点（宽限期状态机 + 幂等）。
- [ ] 前端 user-keys-card 增加轮换 UI（复用既有卡片模式）。
- [ ] 契约守卫 --update + E2E 断言。

**验收标准**：
- [ ] 轮换后新 key 立即可用，旧 key 宽限期内可用，过期后拒绝（401）。
- [ ] 重复轮换不产生脏状态（幂等）。
- [ ] 轮换动作在审计日志有记录（v2.8.0 埋点自动覆盖）。
- [ ] 契约断链=0 + 全量测试绿。

**TDD 清单**：
- [ ] `test_auth_rotation.py`：单值→列表归一化 / 宽限期新旧双可用 / 过期旧 key 拒绝 / 重复轮换幂等 / 环境变量覆盖优先。

### 3.2 审计日志（管理操作留痕）

> ✅ **已落地（v2.8.0，2026-08-05）**：services/audit_service.py（独立 audit-YYYY-MM-DD.jsonl 按天轮转 + 原子写 + 过期整删 + operator 末 8 位脱敏）；require_admin 统一埋点（401/403 必记，写操作与非轮询 GET 成功记，dashboard/`/metrics`/`/health` 轮询 GET 成功降噪防刷爆）；GET /api/audit 读取端点 + 前端 logs 页「审计日志」tab（AuditSection）；`/auth/login` 成功/失败留痕；chatgpt2api_audit_actions_total 指标；test_audit_service.py 20 用例；399 passed / 五道防线全 PASS / E2E 9/9。

### 3.3 敏感信息脱敏（加固）

**现状分析**：token 展示层已末 8 位（accounts 页），审计 operator 已脱敏（v2.8.0），但需系统排查日志/告警/响应中的暴露面。`detail.account_email` 在日志逐条落盘——邮箱本身不算高危，但需确认没有完整 access_token 落盘。

**方案**：
1. 全仓 grep `access_token` 写日志/告警/响应/异常 msg 的暴露点，统一脱敏（保留末 8 位约定，`mask_token()` 工具函数，复用 audit_service._mask_operator 思路）。
2. `alert_service.py` 告警正文、`backup` 快照、`config` 序列化、`/api/settings` 响应中凡含 token 的字段一律脱敏。
3. 新增 `mask_token` 工具 + 全量断言测试。

**验收标准**：
- [ ] grep 确认无完整 token 进入日志/告警/响应/异常消息。
- [ ] 新增脱敏工具单测（边界：空串/短串/含 token 的 URL）。
- [ ] 契约字段不泄漏敏感值。

**TDD 清单**：
- [ ] `test_token_masking.py`：mask_token 边界 / 告警正文脱敏 / settings 响应脱敏 / 日志无完整 token（mock 断言）。

### 3.4 限流默认收紧建议（低风险项）

**现状**：`rate_limit_rpm`/`rate_limit_per_ip_rpm` 默认 0（不限流），内网自用可接受。`production` 下不强制。
**方案**：仅当 `env=production` 且两者皆 0 时，启动打 WARNING 日志提示显式配置（不阻断启动）。
**验收**：production + rpm=0 → 启动日志含明确提示；测试断言该分支。
**TDD**：`test_config.py` 补 production 限流未配置告警分支。

## 4. P0 · 可观测性与运维（v3.4）

> 目标：日志从「文本行」升级为「结构化 + 可过滤 + 可关联」，运维从「看板人工盯」升级为「探针自检 + 指标告警」。

### 4.1 结构化日志

**现状分析**：日志文本行 + `detail` 字段落盘（log_service.py），检索靠正则；`usage_agg` 已做按天切分 + 聚合缓存，但 `/api/logs` 仍只支持 `type/start_date/end_date/account_email/days`。

**方案**：
1. 新增 `structured` 日志模式：JSON Lines，字段 `ts/level/event/request_id/account_email_ms/model/result`，与现有文本并行写（或替代，需评估下游消费方：usage_agg/慢查询/告警）。
2. `/api/logs` 支持结构化字段过滤（`event=`、`request_id=`、`model=`）。
3. 前端日志页增加字段筛选器（复用既有日期/账号筛选模式）。
4. **不破坏现有字段**，向后兼容（旧文本日志仍可读）。

**落地步骤**：
- [ ] log_service 支持结构化行（`json.dumps` 落盘 + 文本兼容读取）。
- [ ] `/api/logs` 增加结构化过滤参数。
- [ ] 前端 logs 页加筛选 UI。
- [ ] 契约 --update + 防线 + 测试。

**验收标准**：
- [ ] 结构化字段过滤返回精确命中（request_id 精确匹配）。
- [ ] 旧文本日志仍可被 `/api/logs` 读取（向后兼容测试）。
- [ ] usage_agg 消费不受影响（回归）。
- [ ] 全量测试绿 + 契约断链=0。

**TDD 清单**：
- [ ] `test_structured_logs.py`：结构化写入 / 文本兼容读 / request_id 过滤 / 字段缺失容错 / 与 usage_agg 消费端回归。

### 4.2 指标扩展

**现状分析**：`/metrics` 已有 `chatgpt2api_upstream_requests_total{model,result}`、备份失败计数、审计动作计数（v2.8.0）、请求延迟等。
**方案**：新增（均在 services/metrics_service.py 或 prometheus_metrics.py 加埋点）：
- `chatgpt2api_scheduler_pick_total{tier}`（调度选取分布）
- `chatgpt2api_lifetime_risk_histogram{risk}`（寿命预测分布）
- `chatgpt2api_redis_fallback_total`（Redis 降级计数，v2.7.1 已有逻辑）
- `chatgpt2api_circuit_breaker_transitions{from,to}`（熔断状态机转移）

**验收标准**：
- [ ] 新指标在 `/metrics` 可见且随事件增长。
- [ ] 每个指标有对应埋点测试。

**TDD 清单**：
- [ ] `test_observability.py` 扩展：各新指标触发一次后计数 +1。

### 4.3 优雅停机与重启自愈增强

**现状**：优雅停机已接 session_pool.close_all + 守护线程 join 5s（app.py lifespan）；bat 崩溃自动重启 + 指数退避。
**方案**：
1. 重启前把 `c2api_restart.log` 尾部 50 行写入 crash 摘要（`data/crash_last.json`），下次启动看板展示「上次崩溃摘要」。
2. 若 5 次熔断后不再自动重启（bat 现有逻辑），加「人工确认恢复」提示（bat 内 echo）。
3. 新增 `/api/system/healthz` 存活探针（无鉴权，供容器/docker healthcheck）。

**验收标准**：
- [ ] 崩溃后 `data/crash_last.json` 生成且含尾部日志。
- [ ] `healthz` 返回 200 空 JSON（供 docker healthcheck）。
- [ ] bat 5 次熔断后提示人工介入。

**TDD 清单**：
- [ ] `test_healthz.py`：healthz 200 / 不依赖存储。
- [ ] crash 摘要生成纯函数单测。

### 4.4 依赖健康自检

**现状**：无对存储/Redis/上游连通性的主动自检端点。
**方案**：新增 `GET /api/system/health/ready`：检查存储可写、Redis（若配置）连通、返回各依赖状态 + 耗时。
**验收**：依赖不可用时返回 503 + 具体原因，可用时 200。
**TDD**：`test_health.py`：存储 mock 不可写 → 503；Redis mock 断连 → 降级标记。

> 目标：把「能出图」升级为「更好用的出图平台」——收藏、批量、配额、告警策略。

### 5.1 图片工作台增强（历史收藏 + 批量下载）

**现状**：image/page.tsx 1829 行，已有会话/画廊/任务三套逻辑；image-manager 776 行支持管理。
**方案**：
1. 图片「收藏」：image_tags_service.py 已存在打标签能力，复用为收藏（加 `favorite` 标签/字段）。
2. 批量下载：前端画廊多选 + 打包 zip 下载（后端复用 export_editable 思路，或前端 JSZip 前端打包）。
3. 生成历史按「prompt 相似」去重展示（复用 find_conversation_by_prompt 思路做前端分组）。

**验收标准**：
- [ ] 收藏的图片在 image-manager 有独立筛选。
- [ ] 批量下载产出合法 zip（后端或前端两条路选一，禁重复造轮子）。
- [ ] 契约 + E2E。

### 5.2 批量生成任务

**现状**：图片任务为单张提交（image_task_service.py），无「一次提交 N 张不同 prompt/参数」的批量任务。
**方案**：
1. 新增 `/api/image-tasks/batch`：接收数组，串行/受限并发（`image_account_concurrency` 约束）执行，返回批量任务 id + 进度。
2. 前端图片工作台增加「批量生成」模式（多 prompt 文本域，每行一张）。
3. 进度 SSE/轮询复用既有 `resume_poll` 机制。

**验收标准**：
- [ ] 批量任务中途失败不影响其他项（隔离）。
- [ ] 并发受 `image_account_concurrency` 约束（不超发）。
- [ ] 契约 + 测试。

### 5.3 用量/配额管理增强

**现状**：容量报表（capacity）基于聚合缓存已落地；但无「按 API key / 按调用方」的用量统计。
**方案**：
1. 若引入多 key（3.1），用量统计按 `Authorization` 身份分组（`chatgpt2api_usage_by_key_total`）。
2. 看板增加「用量排行」卡片（Top 调用方）。

**验收标准**：多 key 下用量可按 key 过滤；契约字段对齐。

### 5.4 告警策略增强

**现状**：6 类告警事件 + 5 分钟去重 + 恢复事件已闭环；审计动作计数（v2.8.0）可辅助告警溯源。
**方案**：
1. 告警阈值可配置（如 healthy 占比 < 阈值告警——账号池健康度）。
2. 告警模板支持变量（`{healthy_count}`/`{total}`/`{riskiest_account_ms}`）。
3. 前端设置页告警区增加阈值输入。

**验收标准**：阈值触发 / 模板渲染正确 / 去重生效。

## 7. P1 · 架构演进（v4.0）

> 目标：把「巨型文件 + 硬编码协议」升级为「内聚模块 + 可插拔协议」，为 v5.x 打地基。

### 7.1 services/openai_backend_api.py（2977 行）拆分

**现状**：单文件承载 OpenAI 兼容后端适配、上游 API 调用、图片/文本请求组装、OAuth/代理参数注入；`class OpenAIBackendAPI` 方法量大，与 session_pool/proxy_service 强耦合。

**方案（按调用面切片，对外零破坏）**：
1. `services/openai_backend/` 包替代单文件，`__init__.py` re-export `OpenAIBackendAPI`（所有旧 import 路径不动）。
2. 切片：`session_utils.py`（会话/代理/参数组装）、`image_payloads.py`、`text_payloads.py`、`response_parse.py`（响应解析/错误归一）、`backend_api.py`（主类只留编排）。
3. 每次抽离跑 `test_v1_*.py + test_image*.py + test_chat_completion_cache.py` 防回归。

**验收标准**：
- [ ] `OpenAIBackendAPI` 公开方法签名 diff=0（dir() 对比 + 引用点全绿）。
- [ ] 主类文件 < 800 行，切片 < 400 行。
- [ ] 全量 399+ 绿 + 契约断链=0。

**TDD 清单**：
- [ ] `test_openai_backend_split.py`：包内切片存在 / 主类符号完整 / 公开方法集合与基线快照一致。

### 7.2 services/account_service.py（2038 行）拆分

**方案（调度核心 + 账号仓库两层分离）**：
1. `services/account_scheduler.py`：健康档位 + 调度分 + 选取算法。
2. `services/account_repo.py`：账号增删改查、状态落盘、批量操作。
3. `account_service.py` 保留编排 + record_success/failure 时序 + 对外门面。
4. **关键不变量**：record_success 在可用性确认后调用、`_is_image_account_available` 判定、熔断跳过逻辑原样保留（历史 bug 警示）。

**验收标准**：
- [ ] `get_available_access_token` 候选集合与拆分前一致（快照对比）。
- [ ] 变异探针 caught ≥ 6 escaped=0（调度分公式变异被抓）。
- [ ] 主门面 < 900 行。

### 7.3 协议插件化

**现状**：services/protocol/ 已按协议分文件，但新增协议需改 openai_backend_api.py 主类。
**方案**：
1. 定义 `ProtocolBackend` 抽象基类 + 注册表（`@register_protocol("openai_v1")`）。
2. 主类只做路由分发，协议实现以注册方式接入。
3. **高风险**：必须先写等价性测试（新路由 vs 旧硬编码路径输出一致），再迁移。
**验收**：新协议注册不改主类；等价性测试全绿。

### 7.4 多实例部署指南

**现状**：单机多 worker 已支持；跨机多实例需共享存储（Postgres）+ Redis。
**方案**：产出 `docs/deployment/multi-instance.md`：nginx 负载均衡 + Postgres + Redis + 多实例 systemd/docker 拓扑 + 限流/用量聚合/日志在各实例的分裂取舍。
**验收**：文档完整 + 按文档起 2 实例跑通 smoke。

## 8. P2 · 性能极致（v5.2）

### 8.1 日志读取反向分块（远期，量级触发）

**现状**：`read_text` 全量读，early-exit 只在解析层；按天切分后单文件量级受 5000 条上限约束，风险已可控。
**方案**：`list()` 改 `seek` 尾部倒读分块（复刻 utils/log.py `_SafeStreamHandler` 经验，`errors='replace'` 兜底）。量级突破 10w 行/天再启动。

### 8.2 账号存储增量写

**现状**：json_storage save_accounts 整文件覆写 O(N)。当前量级 <1k 无感。
**方案**：量级突破 1w 前不做；届时切 SQLite（已支持），不在 JSON 上做增量写（避免造轮子）。

### 8.3 前端 bundle 瘦身

**现状**：dashboard 引入 recharts（大库）；image 页可能整包引 lucide。
**方案**：recharts 改具名导入 / 动态 import；lucide 已树摇（确认）；`next/dynamic` 拆分首屏。
**验收**：`web/out` bundle 体积对比 + Lighthouse 首屏指标。

## 9. P2 · 前沿能力（v5.3）

> 目标：在既有「ChatGPT 逆向封装」基础上，扩展工程化与智能化能力。

### 9.1 多模型路由

**现状**：`default_upstream_model_name` 单一默认模型；model_service.py 已有模型目录。
**方案**：按请求参数路由（`model` 显式 / 兜底默认），支持「多上游模型 → 同 OpenAI 接口」的映射表配置。
**验收**：`/v1/models` 返回映射表；请求按 model 路由正确。

### 9.2 AI 内容审核（可选，谨慎）

**现状**：content_filter.py 已有敏感词过滤（sensitive_words）。
**方案**：接入 `ai_review` 配置（已有 base_url/api_key/model/prompt 字段，目前 enabled=false）做图片/文本后置审核——先评估调用方是否真的需要，避免过度工程。

## 10. 工程质量门禁（每批次必过）

### 10.1 测试策略

- 单元 + 集成 + E2E 三层次；覆盖率目标：**新增逻辑 ≥90%，关键模块（调度/熔断/连接池/日志/告警/审计）向 100% 冲刺**。
- 活测试（live/redis 标记）不触网，本地手动 `uv run pytest -m live`。
- 变异探针是「测试真能抓住回归」的守门员：任何新逻辑必须能通过种子变异被抓，否则补测试。

### 10.2 五道防线（scripts/run_all_guards.py）

| 防线 | 通过标准 |
|------|---------|
| 契约守卫 | 断链=0，漂移=0（改字段先 --update） |
| SQL 安全审查 | 注入面/事务/多 worker 守卫 0 告警 |
| 慢查询猎杀 | 本轮热点从清单移除（附报告） |
| 变异探针 | caught ≥ 6，escaped=0 |
| 极限施压 | 并发突刺 + 慢存储注入 + 并发写一致性 PASS |

### 10.3 E2E 冒烟

前端改动跑 `scripts/e2e_smoke.cjs`；新增交互反馈断言持续扩展。真实浏览器 + 真实服务，禁 mock 充数。**改前端后必须同步 web_dist**（`rm -rf web_dist && cp -r web/out web_dist`），bat 仅在 web_dist 缺失时构建。

### 10.4 终局交付门禁

- [ ] 需求追踪：workflow_status.md 有矩阵行 + 证据
- [ ] 反向批判：至少攻击 3 个假设并修复
- [ ] 假功能扫描：前端按钮/开关/菜单必有真实后端调用证据（契约断链=0）
- [ ] 五道防线全绿 + 回归全绿 + 前端 build 成功
- [ ] 文档同步：README/CHANGELOG/onboarding/workflow_status 一致
- [ ] 无伪实现：TODO/FIXME/占位/mock = 未闭环
- [ ] 边界声明：无法实测的写明「做到哪步/缺什么/如何降级」

### 10.5 盲区扫描（每轮至少一次）

1. 最苛刻验收：哪个功能「界面上有、流程走不通」
2. 最倒霉接入方：按文档真实发一个请求会踩什么坑
3. 最辛苦运维：凌晨三点磁盘满/内存涨/连接泄漏会怎样
4. 极端输入：畸形 JSON、超大 body、并发突刺、存储文件被删、config 非法值
5. 时间/环境：时区、系统时间回拨、跨天边界、中文路径、Windows 文件锁
6. 并发与多 worker：状态分裂场景（S1 Redis 已登记，审计/结构化日志同样要注意多 worker 各自写文件）

## 12. 版本规划执行建议

1. **v3.3（安全纵深）+ v3.4（可观测性）优先开工**：二者风险低、无依赖、价值立现——审计日志已闭环（v2.8.0），密钥轮换是最后一个安全短板；结构化日志是 v4.0 拆分与 v5.x 智能化的前提。
2. **v4.0（架构演进）其次**：大文件拆分必须在行为快照测试就位后动手，每抽一个模块跑一次全量。
3. **v5.x（产品/智能/前沿）最后**：依赖 v4.0 的地基，且部分项（多模型路由/AI 审核）需评估真实需求，避免过度工程。
4. **每批顺序**：先 TDD 写测试锁定行为 → 实施 → 全量回归 → 防线 → 文档同步 → 登记 workflow_status。
5. **禁止**：为赶进度跳过防线或 E2E；大文件拆分必须「每抽一个模块就跑一次全量」，不允许一次性大搬移。
6. **保持可回滚**：每个子项独立提交，commit message 遵循 Conventional Commits（feat/fix/refactor/chore + 描述）。
7. **清理旧产物**：每版发版后清理 reports/ 与 final-report-*.html 等中间产物，保持仓库只留最新版本。
