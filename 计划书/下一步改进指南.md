# ChatGPT2API 下一步改进指南（v2.5 → v3.x）

> **定位**：本文件是本项目「计划书」文件夹的核心迭代蓝本，供任何 AI 或开发者据此刻画版本。
> 每一章都是「现状（真实代码依据）→ 问题 → 方案 → 落地步骤 → 验收标准 → TDD 清单」的完整闭环，
> **禁止假实现**：每一条落地后必须跑通测试、防线、E2E，并在 `workflow_status.md` 登记证据。
>
> - 基线版本：**v2.5.0**（337 测试全绿 / 五道防线全绿 / 契约断链=0 漂移=0）
> - 目标版本：v3.0（规模治理 + 性能根治）→ v3.1（产品功能增强）→ v3.2（前端体验）→ v4.0（架构演进）
> - 总原则：**不重构没坏的东西，不重复造轮子**，优先改造既有实现；每个改进独立可回滚。

## 3. P0 · 规模治理（v3.0）

> 目标：把 2977 行的 `openai_backend_api.py`、1993 行的 `account_service.py` 拆成内聚模块，
> 同时不动任何对外行为。**拆分 ≠ 重构**：只做「移动代码 + 最小接口缝合 + 全量回归」，不改变逻辑。

### 3.1 services/openai_backend_api.py（2977 行）拆分

**现状分析（真实代码依据）**：
- 该文件同时承担：OpenAI 兼容后端适配、上游 API 调用、多种图片/文本请求组装、OAuth/代理参数注入。
- 混叠点：`class OpenAIBackendAPI` 内部方法数量级大，且与 `services/session_pool.py`、`services/proxy_service.py` 强耦合。
- 风险：单文件改动极易引发副作用，且 ruff/mypy 对大文件扫描变慢。

**问题**：
1. 职责边界不清：调用侧 `services/protocol/conversation.py` 依赖其内部方法名，一旦误拆破坏契约。
2. 新增模型/后端时需在巨文件里横向翻找，维护成本随版本线性上升。

**方案（推荐「按调用面切片」而非「按协议切片」）**：
1. `services/openai_backend/` 包替代单文件，保持 `OpenAIBackendAPI` 类名与公开方法签名不变（对外零破坏）。
2. 切片：`session_utils.py`（会话/代理/参数组装）、`image_payloads.py`（图片请求 body 构造）、`text_payloads.py`（文本请求 body 构造）、`response_parse.py`（上游响应解析/错误归一）、`backend_api.py`（主类，只留编排）。
3. 用 `from .backend_api import OpenAIBackendAPI` 在包 `__init__.py` 重新导出，所有旧 import 路径不动。

**落地步骤**：
- [ ] 建 `services/openai_backend/` 包，先 `__init__.py` re-export `OpenAIBackendAPI`。
- [ ] 用「按方法内聚度」抽离：先抽无依赖的纯函数（payload 构造、响应解析），再抽 session 相关，最后留主类。
- [ ] 每次抽离后立即跑 `uv run pytest test/test_v1_*.py test/test_image*.py test/test_chat_completion_cache.py` 确认无回归。
- [ ] 全量 `uv run pytest` + `ruff check` + `mypy`。

**验收标准**：
- [ ] `OpenAIBackendAPI` 公开方法与原文件签名逐一 diff 为 0（用 `dir()` 对比 + 测试引用点全绿）。
- [ ] 全量测试 337 passed / 0 failed。
- [ ] 契约守卫断链=0（未改任何 API 字段）。
- [ ] 文件级行数：主类文件 < 800 行，其余切片 < 400 行。

**TDD 清单**：
- [ ] 新增 `test/test_openai_backend_split.py`：断言包内切片模块存在、主类符号完整、公开方法集合与基线一致（快照对比）。
- [ ] 为每个抽出的纯函数补 1-2 个单测（payload 构造 / 响应解析错误归一），用现有 `test_v1_*` 的 fixture 数据。

### 3.2 services/account_service.py（1993 行）拆分

4. 关键不变量：`record_success` 时序、`_is_image_account_available` 判定、熔断跳过逻辑必须原样保留。

**落地步骤**：

**验收标准**：

## 4. P0 · 性能根治（v3.0）

> 目标：消灭慢查询报告中的剩余热点，让 logs 读取从「全量读盘」变成「分段可控」。

### 4.1 logs.jsonl 按天轮转切分

> ✅ **已落地（v2.6.0，2026-08-05）**：`services/log_service.py` 写 `logs-YYYY-MM-DD.jsonl`、`list(days=N)` 分片读、`delete()` 跨天、`_auto_cleanup()` 两级清理；旧 `logs.jsonl` 惰性迁移；`services/usage_agg.py` 改多文件增量（单例传 DATA_DIR 目录扫 `logs-*.jsonl`，升级检测防 double count）；`/api/logs?days=` 透传 + 前端 logs 页默认近 7 天；慢查询报告移除 3 处日志热点；test_log_rotation.py 11 用例；347 passed / 五道防线 PASS。**4.2 反向分块仍登记远期。**

**现状分析（真实代码依据）**：
- 慢查询报告实测：`logs.jsonl` 714.9KB / 3611 行，热点 `services/log_service.py:128-142 list` 每次全量 `read_text` 再解析。
- `_AUTO_CLEAN_MAX_ENTRIES=5000` 已兜底总量，但高调用量下 5000 条可能只是 1 天量，且单文件读写仍全量。

**问题**：
1. 每次 `/api/logs` 与前端日志页轮询都全量读盘 → CPU+IO 双高。
2. 删除/自动清理整文件重写（`log_service.py:144-164`、`115-126`）在写入高频时放大写放大。

**方案（按天切分，list/usage 只读最近 N 天）**：
1. 新文件命名 `logs-YYYY-MM-DD.jsonl`，当天写入新文件；`logs.jsonl` 作为兼容旧文件的读取兜底（启动时一次性迁移到天文件）。
2. `list()` 支持 `days` 参数（默认 1），只读最近 N 天文件，limit 凑够 early-exit。
3. 删除/清理按「文件级 + 条目级」两级：超 N 天的天文件直接删除（不再重写），当天文件内超 5000 条才逐条裁剪。
4. `usage_agg.py` 已走聚合缓存，不受影响；`_collect_account_health` 若读 logs 需同步改口径。

**落地步骤**：
- [ ] `log_service.py` 增加天文件路径解析 + 当天文件选择 + 兼容旧 `logs.jsonl` 迁移。
- [ ] `list()` 增加 `days` 过滤参数（默认兼容不传 = 读全部，或默认近 7 天，需与前端确认）。
- [ ] 清理逻辑改为「过期天文件整删 + 当天文件裁剪」。
- [ ] `/api/logs` 透传 `days` 参数（api/system.py），前端日志页加时间范围选择。
- [ ] 契约：`/api/logs` 新增参数后跑 `contract_guard --update`。

**验收标准**：
- [ ] 慢查询报告热点「日志列表全量读」「日志删除整文件重写」从清单移除。
- [ ] 新增单测证明：10 天文件场景下 `list(days=1)` 不触碰旧文件（mock 文件系统）。
- [ ] 337+ 新用例全绿；契约断链=0。
- [ ] 数据兼容：旧 `logs.jsonl` 首次启动迁移无丢失（迁移测试）。

**TDD 清单**：
- [ ] `test_log_rotation.py`：
  - 按天写入 → 文件按日期切分正确。
  - `list(days=N)` 只读最近 N 天（mock os.scandir 断言未访问旧文件）。
  - 过期天文件整删，当天文件超限裁剪。
  - 旧 logs.jsonl 迁移无丢失/无重复。
  - `/api/logs?days=` 契约字段存在。

### 4.2 日志读取反向分块（中成本，v3.0 可选）

**现状分析**：`read_text` 仍全量读，early-exit 只在解析层。高 IO 场景（10w+ 行）仍吃全量。

**方案**：`list()` 改用 `seek` 尾部倒读分块（读尾部 1MB → 解析 → 不够再往前），适配 UTF-8 边界用 `errors='replace'` 兜底（复用 utils/log.py 的 _SafeStreamHandler 经验）。
**风险**：编码边界处理复杂。若本轮排期紧，登记 v4.0。

### 4.3 账号存储增量写（仅账号量级 >1w 才做，否则 YAGNI）

**现状**：`json_storage.py:41-43 save_accounts` 整文件覆写，O(账号数)。当前量级 <1k 无感。
**方案**：账号量级突破 1w 前不做；届时直接切 STORAGE_BACKEND=sqlite（已支持），不在 JSON 上做增量写（避免造轮子）。

## 5. P1 · 产品功能增强（v3.1）

> 目标：把「账号存活」这个核心价值从「事后人工处置」升级为「事前预测 + 自动响应」。

### 5.1 账号寿命预测（数据已齐，无需新埋点）

> ✅ **已落地（v2.7.0）**：services/account_lifetime.py（EWMA 失败率+连续失效窗口双信号，now 可注入）；调度降档（只降不升+最小观测窗口防抖动）；scheduler/accounts API 附加 lifetime_*；dashboard 濒危卡片+寿命列、accounts 寿命徽章；test_account_lifetime.py 17 用例。

**现状分析（真实代码依据）**：
- 每账号 `success`/`fail` 计数落盘（account_service.py:317-318，调度分直接消费）。
- 最近错误时间戳 `last_refresh_error_at`/`last_token_refresh_error_at` 已存在并参与冷却惩罚。
- 日志逐条含 `detail.account_email`，可回溯单账号成败时间线。
- **结论**：预测所需输入全部存在，只需把「已消费的同一批信号」改写成趋势形态（近 N 次失败率斜率）。

**方案**：
1. 新增 `services/account_lifetime.py`：输入每账号 `success/fail/错误时间戳` 序列，输出 `lifetime_risk`（低/中/高/濒危）+ 预估剩余可用时长。
2. 算法（第一性原理）：用「近 N 次请求的指数加权失败率」EWMA + 「连续失败窗口」双信号，不引入统计回归（数据量小，EWMA 更稳）。
3. 调度接入：`_account_health_tier` 将 lifetime_risk 作为降档信号（高/濒危 → warm/risky），不直接封禁。
4. 看板接入：账号页新增「寿命预测」列/徽章，dashboard 增加「濒危账号」卡片。
5. 告警接入：`alert_service.py` 新增事件 `account_lifetime_critical`，预测濒危时 webhook 推送（复用既有去重机制）。

**落地步骤**：
- [ ] 纯函数实现 `compute_lifetime_risk(history)`（EWMA + 失败窗口），写单测锁定。
- [ ] 调度降档接入 + 回归。
- [ ] 看板/账号页展示 + 契约更新。
- [ ] 告警事件接入 + 去重测试。

**验收标准**：
- [ ] 构造 3 类历史（健康/偶发失败/连续失败），预测档位符合预期。
- [ ] 调度不因预测值出现「瞬间封禁/复活抖动」（冷却 + 最小观测窗口守卫）。
- [ ] 前端列/卡片有真实后端数据来源（契约断链=0，禁假接口）。

**TDD 清单**：
