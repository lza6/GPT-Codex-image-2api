# ChatGPT2API 下一步改进指南（v1.9.0 → v2.0.0）

> 创建时间：2026-08-02
> 适用版本：当前 v1.9.0（6 阶段已闭环：启动脚本 / 7×24 守护 / 智能调度 / 运维看板 / 高并发 / 终局审计）
> 本文档性质：**只出计划与修改指南，不含代码实现**。交由执行方按阶段落地，每个阶段附 TDD 清单与验收标准。
> 核心约束（必须遵守）：
> 1. **不大幅度重构任何文件**——只在现有基础上修改、改进、迭代；禁止重写、重建。
> 2. **不重复造轮子**——动手前先检查项目内是否已有实现（services/、utils/、api/），优先改造现有模块。
> 3. **先修 bug 再加功能**——严格按本文档阶段顺序执行，禁止跳跃。
> 4. **每阶段必须闭环**——测试跑通 + 实际运行验证 + 更新 docs/workflow_status.md 后才算完成。
> 5. **清理旧产物**——每次升级后删除被替代的旧代码/旧文件/旧配置，不留屎山残留。

## 第一部分：项目现状评估（事实基础）

### 1.1 架构现状

```
客户端 → FastAPI (api/) → services/protocol/（协议适配层）
                            ↓
                     services/openai_backend_api.py（上游调用，2763 行）
                            ↓
                     services/account_service.py（号池调度，1839 行）
                            ↓
                     services/storage/（json / sqlite / postgres / git 四后端）
前端：Next.js 16 + React 19 + Tailwind 4 + zustand（web/，构建产物 web_dist/）
```

- 入口：`main.py` → `api/app.py`（lifespan 管理 3 个守护线程：account-watcher / image-cleanup / backup）
- HTTP 客户端：`curl_cffi.requests.Session`（同步），FastAPI 侧用 `run_in_threadpool` 包装
- 测试：38 个测试文件、约 170 个测试函数（pytest + httpx/TestClient）
- 压测基线：4 Worker 7912 req/min（docs/PLAN.md 记录）

### 1.2 已具备的能力（不要重复造）

| 能力 | 位置 | 状态 |
|------|------|------|
| 健康档位调度（healthy/warm/risky + 调度分 + 双模式 + 优先级） | services/account_service.py:1001-1056 | ✅ |
| 滑动窗口限流（全局 RPM + 单 IP RPM） | api/rate_limit.py | ✅ |
| 代理池（健康检查/隔离/三种选择策略） | services/proxy_pool.py、api/proxy_pool.py | ✅ |
| 多 Worker 启动 | main.py（config.workers） | ✅ |
| 运维看板（3 API + 前端页） | api/dashboard.py、web/src/app/dashboard/ | ✅ |
| 自动备份（R2，轮转/加密） | services/backup_service.py | ✅ |
| 敏感词过滤 + AI 二审 | services/content_filter.py | ✅ |
| 聊天缓存 | services/protocol/chat_completion_cache.py | ✅ |
| Windows 一键启动/停止 | 启动chatgpt2api.bat、停止chatgpt2api.bat | ✅ |

### 1.3 关键短板（按严重程度排序，改进目标即来源于此）

| # | 短板 | 证据 | 风险 |
|---|------|------|------|
| S1 | **多 Worker 状态不共享**：限流计数、调度索引 `_index`、健康档位、聊天缓存全部在单进程内存 | api/rate_limit.py 进程内 deque；services/account_service.py:54 `self._index` | 4 Worker 时实际限流阈值 = 配置值 ×4；调度退化为近似随机；缓存命中率 ÷4 |
| S2 | **无可观测性**：无 Prometheus 指标、无结构化日志、无请求追踪 ID | 全项目无 metrics 端点 | 生产故障只能翻文本日志，无法定位慢请求/错误率突增 |
| S3 | **上游调用无熔断/重试分级**：账号失败靠健康档位被动降权，无主动熔断器；429/5xx 处理散落在各处 | services/openai_backend_api.py `_raise_on_error` | 上游抖动时请求排队打到坏账号，雪崩风险 |
| S4 | **OpenAIBackendAPI 每请求新建 Session**：无跨请求连接池复用 | services/protocol/conversation.py:710/724/1343 每次 `OpenAIBackendAPI(...)` | TLS 握手开销 ×N，高并发下延迟尾巴长 |
| S5 | **安全默认值偏弱**：CORS `allow_origins=["*"]`；config.json 默认 auth-key 为明文 "chatgpt2api"；无请求体大小限制 | api/app.py:44-50；config.json | 被扫到即被白嫖/打满 |
| S6 | **巨型文件维护性差**：openai_backend_api.py 2763 行、account_service.py 1839 行、conversation.py 1644 行 | wc -l | 改一处怕全身，review 困难（注意：治理方式是"温和拆分"，不是重写） |
| S7 | **前端无实时性**：看板/日志/账号状态靠手动刷新，无 SSE/WebSocket 推送；操作反馈（toast/loading）不统一 | web/src/app/dashboard/page.tsx | 7×24 运维场景体验差 |
| S8 | **无 CI/CD**：无 GitHub Actions，测试靠手跑；无依赖漏洞扫描 | .github/ 仅 copilot-instructions.md | 回归风险全靠人 |
| S9 | **config.json 单文件膨胀**：2.9KB 混杂代理/备份/调度/内容过滤等全部配置，无分组校验 | config.json | 改配置易出错，无启动时 schema 校验 |

## 第二部分：改进总目标（v2.0.0 定义）

**一句话：从"单机可用"升级为"生产可信"——状态可共享、故障可观测、上游可熔断、安全可兜底。**

| 维度 | v1.9.0 现状 | v2.0.0 目标 | 度量 |
|------|------------|------------|------|
| 分布式状态 | 单进程内存 | Redis 可选接入（不装 Redis 时完全回退现有行为） | 4 Worker 限流计数误差 < 5% |
| 可观测性 | 文本日志 | /metrics + 结构化日志 + 请求 ID 全链路透传 | 任意请求可在日志中按 ID 串联 |
| 上游韧性 | 被动降权 | 熔断器（半开探测）+ 统一重试预算 | 上游 5xx 风暴时 P99 延迟不翻倍 |
| 连接复用 | 每请求新建 | 按账号复用 Session（带 TTL + 泄漏保护） | 长会话 P50 延迟下降 ≥20% |
| 安全 | 宽松默认 | 生产模式默认收紧 + 启动安全检查清单 | 默认配置通过安全基线检查 |
| 前端体验 | 手动刷新 | 看板 SSE 实时推送 + 统一操作反馈 | 看板数据延迟 ≤5s |
| 质量保障 | 手跑测试 | CI 四道门（lint/type/test/security） | 每次提交自动跑 170+ 测试 |

### 阶段 3：上游韧性——熔断器 + 统一重试预算 + Session 复用（P0，2.5 天）

**目标**：消除 S3、S4。这是单机体验提升最大的一步。

- [ ] 3.1 **熔断器**（新增 services/circuit_breaker.py，小文件 <200 行，自己实现即可，不引重依赖）
  - 状态机：closed → open（连续失败 ≥5 或 60s 内失败率 >50%）→ half_open（30s 后放行 1 个探测）→ closed
  - 按"账号 + 失败类别"维度：token 失效类立即 open 并联动现有健康档位降级；429 类走现有 warm/risky 逻辑不动
  - 与 account_service.py 的集成方式：**在选取账号后、发起上游调用前检查熔断表**（改 services/protocol/conversation.py 的取号点，不改调度算法本身）
  - open 状态账号在调度分中直接过滤（复用现有 `_filter_*` 链，加一个过滤条件）
- [ ] 3.2 **统一重试预算**
  - 收敛散落的重试逻辑：只允许两类重试——①幂等 GET（_get_me/_get_conversation 等）指数退避最多 2 次；②流式首字节前连接失败换账号重试最多 1 次
  - 流式开始后**绝不重试**（会重复扣费/重复出图），只断流报错
  - 在 openai_backend_api.py 增加统一的 `_request_with_budget` 私有方法，各调用点逐步迁移（**逐点改造，不一次性大改**）
- [ ] 3.3 **Session 复用池**（新增 services/backend_session_pool.py）
  - 按 access_token 复用 `OpenAIBackendAPI` 实例（含其 curl_cffi Session）：LRU 容量 64、TTL 30min、引用计数归还
  - 改造 conversation.py:710/724/1343 三处实例化点为池化获取（`with pool.acquire(token) as backend:`）
  - token 轮换/失效时必须主动驱逐（account_service 刷新 token 处调用 `pool.evict(old_token)`）
  - 进程退出时 lifespan finally 里统一 close，防句柄泄漏
- [ ] 3.4 **压测对比**：用阶段 0 的基线方法重压，记录 P50/P95/错误率对比，写入 workflow_status.md（预期 P50 下降 ≥20%）

**TDD 清单**：
- `test/test_circuit_breaker.py`（新建）：状态迁移 closed→open→half_open→closed 全覆盖；open 期间取号被跳过
- `test/test_backend_session_pool.py`（新建）：同 token 两次获取是同一 Session；LRU 逐出；TTL 过期；evict 生效；并发获取线程安全

### 阶段 4：Redis 可选共享状态（P1，2 天）——让多 Worker 名符其实

**目标**：消除 S1。**设计原则：Redis 是可选增强，不装 Redis 行为与现状完全一致**（零依赖回归风险）。

- [ ] 4.1 **抽象共享状态层**（新增 services/shared_state.py）
  - 接口：`incr_window(key, window_seconds) -> int`（限流计数）、`next_index(key, modulo) -> int`（轮询游标）、`cache_get/cache_set`（聊天缓存）
  - 双实现：`LocalSharedState`（现有内存逻辑原样搬入）+ `RedisSharedState`（redis-py + Lua 脚本保证滑动窗口原子性）
  - 工厂按 `REDIS_URL` 环境变量选择；连接失败自动降级 Local 并打 WARNING（**不允许因 Redis 挂了导致服务不可用**）
- [ ] 4.2 **限流中间件迁移**（api/rate_limit.py）：计数器改用 shared_state，行为不变；多 Worker 下全局限流终于准确
- [ ] 4.3 **调度轮询游标迁移**（account_service.py `self._index`）：round_robin 模式游标走共享状态
- [ ] 4.4 **聊天缓存迁移**（services/protocol/chat_completion_cache.py）：后端可切换到 Redis（带 TTL），Local 实现保留
- [ ] 4.5 **健康档位跨进程同步**（可选，复杂度高则降级为文档说明）：各 Worker 定期把档位快照写 Redis，选取时合并视图；如工期紧张此项可砍，文档注明"各 Worker 独立评估档位，Redis 仅共享计数与游标"即可
- [ ] 4.6 docker-compose.yml 增加可选 redis service（profile 隔离，默认不启动）；.env.example 增加 `REDIS_URL` 注释说明

**TDD 清单**：
- `test/test_shared_state.py`（新建）：Local 实现行为与现状一致（窗口计数/游标/缓存 TTL）
- Redis 实现用 fakeredis 或 monkeypatch 客户端做单测（CI 不依赖真 Redis）
- 集成测试（手动/docker）：两进程同时压限流接口，总数不超阈值 ×1.05

**验收**：无 Redis 时全部现有测试不回归；有 Redis 时 4 Worker 限流误差 <5%。

## 第四部分：风险与权衡（提前说清）

| 决策 | 权衡 | 理由 |
|------|------|------|
| Redis 做可选而非必选 | 多一层抽象成本 | 大量用户单机跑 bat，强制 Redis 会提高门槛；Local 回退保零回归 |
| 熔断器自研而非引库 | 重复造轮之嫌 | 需求仅三态机 + 计数，pybreaker 类库反而带来事件模型不匹配；<200 行可控 |
| Session 池按 token  keyed | 账号多（>64）时 LRU 逐出频繁 | 64 容量覆盖绝大多数部署；逐出只是回到现状（新建），无正确性风险 |
| 巨型文件拆分而非重写 | 收益渐进 | 遵守"不大幅重构"红线；提取式拆分风险最低，测试即安全网 |
| /metrics 需鉴权 | 多一步配置 | 指标含账号规模等敏感信息，公网裸奔不可接受 |
| 活测试标记移出 CI | 覆盖率数字下降 | 触网测试在 CI 必然 flaky；本地手动跑保留，CI 门禁必须稳定 |
